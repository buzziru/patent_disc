17대분류 / 188중분류, 출처 KIPRIS(한국 공개/등록). 원본 설명서: `data/과학기술표준분류 대응 특허데이터_데이터설명서.pdf`.
`data/`는 `.gitignore` 대상이라 커밋되지 않는다(전체 419MB).

> **건수 주의**: 공식 문서의 `300,240`은 고유 문서 수가 아니라 **(문서, 레이블) 쌍 수**다. 한 특허가 여러 중분류 zip에 중복 수록되므로(→ 다중 레이블) 고유 특허 수는 그보다 적다. **로컬 스냅샷** 실측: (문서,레이블) 쌍 270,216 / **고유 documentId 224,328**(Training 202,860 · Validation 29,290, 단 **7,822건이 양 폴더에 겹침**). 로컬은 업체 `datadam_20230116` 버전과 다른(작은) 스냅샷이다.

## 레이아웃

```
data/
  Training/   Validation/
    Orig/    ← 입력(TS_… .zip)  — 188개 zip = 188개 중분류
    Label/   ← 정답(TL_… .zip)  — 188개 zip = 188개 중분류
```

- zip 파일명은 중분류 단위: `TS_TS1_<대분류코드>_<대분류명>_<중분류코드>_<중분류명>.zip` (라벨은 `TL_TL1_…`).
- 각 zip 안에는 특허 1건당 JSON 1개. **파일명(= `documentId`, 예 `kr20020059117b1`)으로 원천↔라벨을 조인**한다.
- 압축 해제 시 파일 수가 많으므로 **`zipfile`로 zip 내부 JSON을 직접 스트리밍**하는 것을 권장(`unzip -p <zip> <name.json>`으로 단건 확인).

## JSON 스키마

두 파일 모두 최상위 `dataset` 키 아래에 필드가 있다.

**원천데이터**(입력): `invention_title`, `abstract`, `claims`, `applicant_name`, `open_date`/`application_year`/`register_date`, IPC 필드(`ipc_main`, `ipc_section`, `ipc_class`, `ipc_subclass`, `ipc_all`) 등.
→ 분류기 입력 후보 텍스트 필드: **명칭(`invention_title`) · 요약(`abstract`) · 청구항(`claims`)**. 표본 실측 존재율 ~100%(`invention_title` 100%, `abstract`·`claims` 99.9%). **별도 `상세설명` 필드는 없다** — 장문의 실체는 주로 `claims`. 어떤 필드를 쓰는지가 장문 처리 실험의 핵심 축.

**라벨링데이터**(정답): `documentId`, **`Lno`**(대분류 코드, 예 `EA`) / `Ltext`(예 `기계`), **`Mno`**(중분류 코드, 예 `EA01`) / `Mtext`, `ipc_main`, `country_code`, `document_type` 등. 파일이 든 zip명 자체가 그 문서의 `Mno`를 인코딩(`TL_TL1_EG_원자력_EG10_핵융합.zip` → `EG10`).
→ 학습 타깃은 **문서별 `Mno` 다중-핫(188-class, multi-label)**. 한 특허가 여러 `Mno`를 가질 수 있다. `Lno`(대분류)는 **예측된 각** `Mno` → `Lno` 매핑으로 유도(별도 Lno 헤드 불필요 → 계층 일관성 유지).

## 17개 대분류

## 주의 (분포·비교)

- **다중 레이블(multi-label)**: 한 특허가 여러 중분류에 대응한다. 로컬 Training 실측 — 고유 문서 202,860 중 문서당 서로 다른 `Mno` 개수 분포 `{1: 174,275, 2: 22,282, 3: 4,617, 4: 1,128, 5: 396, 6: 134, 7: 20, 8: 7, 10: 1}` → **다중 Mno 문서 28,585건(14.1%)**, 평균 ~1.2개. 학습 타깃은 문서별 다중-핫 벡터(sigmoid+BCE).
- **분할 누수 주의**: 제공된 `Training`/`Validation` 폴더는 **7,822개 documentId가 양쪽에 중복**된다. 문서 단위로 집계 후 **`documentId` 기준 재분할**해야 누수가 없다.
- **벤더 폴더 단위 라벨 산포(단일-라벨 관점의 충돌)**: 벤더는 라벨을 `(documentId, Mno)` 단위 단일-라벨 레코드로 저장한다(JSON 1개 = Mno 1개, zip명이 Mno 인코딩). 다중-`Mno` 특허는 여러 zip에 흩어지며, 층화 분할이 그 조각을 두 폴더로 나눠 담아 위 7,822건이 생긴다. 이 겹침 문서는 Training·Validation의 `Mno` 집합이 **완전히 배타**(교집합 0)라 단일-라벨 관점에서 "같은 문서를 한 폴더에선 X, 다른 폴더에선 Y로" 취급하는 충돌로 보이나, **모순이 아니라 다중-라벨의 서로 다른 조각**이다(합집합이 참 라벨). 라벨 주석 자체는 무결하다 — 원본 라벨 270,216건 전수 검사에서 JSON의 `Mno`↔소속 zip, `Lno`↔`mno2lno[Mno]` 불일치 **0건**. `documentId` 합집합 집계가 이 조각을 다중-핫 1행으로 재조립(→ MLC)하며 겹침도 해소한다(검출 노트북 `../../notebook/10_03_Label_Conflict_Clean.ipynb`).
- **`documentId` dedup의 사각 — 입력 동일 케이스(제거 완료, 총 336문서)**: `documentId`는 특허 **문서**를 식별하지 **정규화된 모델 입력**을 식별하지 않는다. 같은 출원의 공개(`a`)·등록(`b1`) 문서나 가족/분할 출원은 서로 다른 `documentId`인데 모델 입력(`invention_title + ipc_main + abstract + claims`, 빈 필드 skip)이 **바이트 단위로 동일**할 수 있다. `documentId` 기준 dedup은 이를 걸러내지 못한다. 모델 입력 문자열 동일성으로 전 split을 재검출해 네 부류를 제거했다(`../../notebook/10_03_Label_Conflict_Clean.ipynb`, SSOT `output/label_conflict_docs.json`):
  - **라벨 충돌 89문서**(42그룹) — 같은 입력에 `Mno`가 다름(공개/등록 + 출원번호가 다른 near-dup). 어느 라벨이 옳은지 판정 불가라 그룹 전원 제거.
  - **train 내 정확-중복 199문서** — 같은 입력·같은 라벨이 train에 중복 → 사본 1개만 유지.
  - **eval 정확-중복 누수 45문서**(val 20 + test 25) — 같은 입력·같은 라벨이 train과 eval 양쪽에 존재 → train 사본 유지, eval 사본 제거(암기 채점 방지).
  - **val+test 정확-중복 3문서** — train은 없고 같은 입력·같은 라벨이 val·test에 걸침 → test 사본 유지, val 사본 제거.
  - 제거 후 train 201,616 / val 11,132 / test 11,244(총 223,992), 잔여 충돌 0. **재토큰화는 하지 않았다** — 토큰화본이 `document_id`를 유지하고 원본과 행 순서가 동일하며 토큰화가 행별 결정적이라, 원본·토큰화본을 같은 `document_id` 집합으로 필터링하면 재토큰화와 동일한 결과가 된다. 남은 것: val 전용 등 같은 split 내 정확-중복(누수 아님, 유지).
  - **로짓 행 축 SSOT는 두 벌이다**(로짓 파일은 데이터셋 행 순서를 전제하므로 축을 섞으면 안 된다):
    - `output/doc_ids_{val,test}.json` — **구** 로짓(exp2·KoBERT·손실 3종, val 11,162 / test 11,271)의 행 축. **과거 코드 재현용으로 유지**하며 덮어쓰지 않는다.
    - `output/doc_ids_clean_{val,test}.json` — **정리** 로짓(b128 등 clean-data 런, val 11,132 / test 11,244)의 행 축 = 정리 데이터셋 `document_id` 순서. 구 축에서 제거 336건을 순서 보존해 뺀 것과 동일(생성·검증 스크립트는 `scratchpad`). 구 로짓을 정리 축에 얹을 때는 `doc_ids_{split}` → `doc_ids_clean_{split}` 사영으로 정렬한다(`../../notebook/11_02_CleanData_Error_Analysis.ipynb`).
  - 참고로 `application_number`↔`documentId`는 1:다이며(공개/등록 등 628쌍이 한 출원에 2 문서), `documentId`↔입력 텍스트·출원번호는 충돌 0으로 문서 식별키로는 무결하다.
  - **충돌 클래스의 낮은 F1은 클리닝 이득의 근거가 아니다 — 공통 원인(class ambiguity)**: exp2(modern512) per-class F1에서 충돌 연루 74클래스 평균 F1 **0.8315**가 비연루 114클래스 **0.8738**보다 **4.2pt 낮다**(support는 양쪽 72로 동일 — 클래스 크기 효과 아님). 그러나 충돌 문서는 연루 클래스당 train의 <0.5%라(EB01조차 7/~1,500) 4.2pt를 **인과적으로 만들 수 없다.** 모호한 중분류일수록 분류가 어려워 F1이 낮고 동시에 어노테이터가 갈려 충돌 라벨이 붙으므로, 충돌은 낮은 F1의 **원인이 아니라 marker**다(공통 원인 = class ambiguity). 방증: 전체 최저 F1 클래스 EG09(0.5785)는 충돌과 무관하다. 따라서 89건 제거로 회수될 몫은 볼륨에 묶여 작고 갭 대부분은 클리닝 후에도 남을 것으로 예상되며, 클린 재훈련의 clean-data 효과는 aggregate가 아니라 연루 클래스(특히 EB01 0.8189)의 per-class 선택적 상승 여부로 판정한다(per-class 베이스라인 SSOT `output/per_class_f1_modern512.json`, 계산 `scratchpad` 기준 재현 가능).
- **제공된 Training/Validation은 라벨별 1/9 층화 분할**: zip(=Mno) 멤버 수 실측 — (문서,라벨) 쌍 Training 240,192 / Validation 30,024. 라벨별 검증 분율 `v/(t+v)`가 **전 188개 중분류에서 상수 0.111(=1/9), sd 0.000**이며 train_share↔val_share 상관 **0.9998**. 즉 제공 분할은 랜덤이 아니라 **각 zip을 9:1로 쪼갠 층화 분할**이다(전체 표 산출 스크립트는 `scratchpad/label_dist.py`). → 재분할할 때도 **라벨 분포를 보존하는 층화 분할을 써야 이 기준선과 정합**한다. 단순 `train_test_split`(비율만, 비층화)은 188-way·희소 클래스(train 최소 406건)에서 검증셋 라벨 분포를 왜곡한다.
- **인위적으로 평탄화된 분포**: 중분류당 대체로 1,300~2,600건. 실제 출원 분포와 다르므로 결과 해석 시 한계로 명시.
- **`0.8249`는 top-1 예측의 weighted-F1**(full test 24,525건 실측 — Micro 0.8261 / Macro 0.8038). baseline 데이터 분할은 **`documentId`가 train·val 양쪽에 존재하는 데이터 누수** 위험이 있어, **누수 없는 데이터셋을 새로 생성**하고 자체 test 고정 + KoBERT 자체 재현으로 비교선을 세운다(`../../PROJECT.md` 평가 절, 재현 절차 `../experiments/kobert-baseline.md`).

### 라벨 카디널리티(k) 세부 분포

문서별 정답 `Mno` 개수 `k`를 값별로 분해한 것(정리 test 11,244, `document_id` 조인). `k≥2`로 뭉치지 않고 값 단위로 본다. 산출 스크립트 `scratchpad/k_distribution.py`, SSOT `output/k_distribution_analysis.json`. 평균 `k=1.204`, 최대 8.

| k | 문서 | 문서 비율 | 양성 인스턴스 | 양성 비율 |
| --: | --: | --: | --: | --: |
| 1 | 9,555 | 84.98% | 9,555 | 70.60% |
| 2 | 1,275 | 11.34% | 2,550 | 18.84% |
| 3 | 298 | 2.65% | 894 | 6.61% |
| 4 | 67 | 0.60% | 268 | 1.98% |
| 5 | 33 | 0.29% | 165 | 1.22% |
| 6 | 12 | 0.11% | 72 | 0.53% |
| 7 | 2 | 0.02% | 14 | 0.10% |
| 8 | 2 | 0.02% | 16 | 0.12% |

- **분포는 극단적으로 k=1에 쏠린다** — 문서의 85%가 단일 라벨이나 양성 라벨 인스턴스로는 70.6%다. `k≥2`는 문서의 15.0%지만 양성 인스턴스의 **29.4%**를 차지해 micro-F1(인스턴스 가중)에 실리는 무게가 문서 비율의 두 배다. 코퍼스 전체 다중-Mno 비율(14.1%, 위 「주의」)과 정합한다.
- **k는 문서 길이와 거의 독립이다.** `kobert_len` 평균이 k=1 895 / k=2 857 / k=3 885 토큰으로 사실상 평평하다(k≥4는 문서 <70건이라 추정 불안정, k=5의 p90 3,034은 소표본 꼬리). 다중 라벨은 **장문의 산물이 아니다** — long-document 축과 별개의 구조다.
- **다중 라벨은 대분류 2개 안에 몰린다.** 정답이 걸친 서로 다른 `Lno` 수는 k=2 1.55 / k=3 1.94 / k=5 2.70으로 `k`보다 훨씬 느리게 는다. k=2 문서의 **45%는 한 대분류 안의 형제 중분류 쌍**(단일 Lno 내)이고 나머지가 대분류를 가로지른다.
- **고카디널리티는 특정 도메인에 편중된다.** 지배 대분류가 k=1의 LB·EE·EA에서 `k≥3`은 **ND·EH·EG**로 옮겨간다(양성 인스턴스 상위 기준).
- **k별 F1 성능·오라클-k 헤드룸의 분해는 데이터 축이 아니라 평가 축**이므로 `../experiments/modernbert-comparison.md`(k 분해)와 `../experiments/cardinality-decoding.md`가 소유한다 — 요지는 `k=1→k=2`에서 micro가 급락(−8.2pt)하고 결손이 랭킹이 아니라 `k≥2` 과소예측(결정 규칙)에 집중된다는 것.

## 입력 토큰 길이 분포 (KoBERT 토크나이저)

`notebook/02_02_KoBERT_Tokenizer.ipynb` 실측. 입력 = `invention_title + ipc_main + abstract + claims` 공백 join(baseline과 동일 필드 조합), `monologg/kobert`(vocab 8,002)로 **truncation 없이** 인코딩한 시퀀스 길이(특수토큰 `[CLS]`/`[SEP]` 포함 → 실토큰 +2).

| split | 문서수     | mean  | median(p50) | p75   | p90   | p95   | p99   | max    | >512 비율 |
| ----- | ------- | ----- | ----------- | ----- | ----- | ----- | ----- | ------ | ------- |
| train | 201,895 | 883.0 | 696         | 1,027 | 1,524 | 2,023 | 4,048 | 10,548 | 71.38%  |
| val   | 11,162  | 881.4 | 698         | 1,025 | 1,506 | 1,981 | 4,137 | 8,827  | 71.39%  |
| test  | 11,271  | 892.5 | 703         | 1,038 | 1,548 | 2,019 | 4,212 | 9,326  | 71.64%  |

세 split의 분포가 사실상 동일하다(mean ~883–893, `>512` ~71.4%) — 재분할이 길이 분포를 왜곡하지 않았다는 확인.

핵심 함의:

- **중앙값(~700 토큰)이 이미 512를 초과** → KoBERT baseline은 **문서의 ~71%를 truncation**하며, 중앙값 문서조차 뒷부분이 잘린다. 뒤에 이어붙는 `claims`가 주로 잘린다.
- **512에서 문서 커버리지 29% vs token recall 54%**(train, 시각화 Viz 2). 커버리지는 all-or-nothing(문서 전체가 들어와야 1)이라 71% 잘림을 그대로 반영하지만, 잘린 문서도 앞 512 토큰은 남으므로 전체 토큰의 54%는 보존된다 — 중앙값이 512 바로 위라 다수 문서가 근소하게만 잘리는 것. baseline이 그럭저럭 도는 이유이자, **정보의 ~46%를 버린다**는 게 장문 인코더 이득의 상한.
- 이 실측이 프로젝트 차별점(**장문 인코더로 512 한계 개선**)의 정량적 근거다 — 512 truncation이 다수 문서에서 실제로 정보를 버린다.
- **A.X-Encoder(16,384) 수용력**: p99 ~4,000, max ~10,500 → 16k면 사실상 전 문서를 무손실 수용, 4,096으로도 ~99% 커버. 시퀀스 길이 sweep 후보(코스트↔커버리지 트레이드오프): 1,024(≈p75) · 2,048(≈p95) · 4,096(≈p99).
- ⚠️ **토큰 수는 토크나이저 의존**: 위 수치는 KoBERT(vocab 8k) 기준이다. A.X-Encoder(vocab 50k)는 문서당 토큰이 더 적게 나오므로 A.X 시퀀스 길이 계획은 그 토크나이저 실측을 따른다 → 아래 「A.X-Encoder 토크나이저 실측」.

핵심 함의:

- **vocab 크기와 압축률은 비례하지 않는다.** KLUE(32k)가 A.X(50k)보다 오히려 압축적이다(0.5369 vs 0.5449). 토크나이저 효율은 vocab 크기가 아니라 학습 코퍼스·분절 방식이 정한다 — "vocab이 크면 토큰이 짧다"는 어림은 KoBERT(8k) 대 나머지에서만 성립한다.
- ⚠️ **A.X-512 vs KLUE-512도 콘텐츠 양이 통제된 비교가 아니다.** KLUE가 문서의 69.4%에서 더 짧아 같은 512 창에 ~1% 더 많은 본문을 담는다(512 무손실 35.78% vs 34.85%). exp2 vs KoBERT를 오염시킨 것과 **같은 종류의 confound가 크기 약 1/10로, 이번엔 대조군 쪽에 유리하게 재발**한다. 크기가 작아 결론을 뒤집을 수준은 아니나, 대조군이 근소하게 이기면 이 성분을 먼저 배제해야 한다(`../experiments/modernbert-comparison.md` 「커버리지 기제의 직접 실측」).
- ⚠️ **KLUE만 `[UNK]` 문제가 실재한다.** 토큰의 0.1495%, **문서의 21.93%가 UNK를 최소 1개 포함**한다(KoBERT는 SentencePiece라 0.0000%, A.X는 1.06%). 특허 텍스트의 기호·수식이 원인으로 추정되며, 대조군 훈련 전에 어떤 문자가 UNK로 떨어지는지 확인해 열화 여부를 판단한다.
- **세 split의 분포가 동일하다**(mean 785.0~793.9, `>512` 63.5~64.2%) — 재분할이 길이 분포를 왜곡하지 않았다는 확인이 세 번째 토크나이저에서도 성립한다.
- ⚠️ **KLUE 컨텍스트는 512로 고정** — max 10,275(train) 토큰인데 실질 창이 512라 **train의 63.5%가 창을 넘긴다**. A.X(16,384)와 달리 절단이 선택이 아니라 필수이며, 무절단본을 그대로 투입하면 position embedding 인덱스 에러가 난다. 절단 규칙은 `../experiments/klue-roberta.md` 「512 창」에 고정했다. 대조군의 역할은 장문 처리가 아니라 **512 창에 묶인 또 하나의 한국어 인코더**로서 모델 성분을 재확인하는 것이다.

### 길이 슬라이스 bin (평가 계층화)

장문 축 검증(`../../owner/problems of vendor's metric.md` 섹션 D의 길이구간별 F1)을 위한 **확정 4구간**. 경계를 **512의 거듭제곱 배수**에 두어 truncation 심각도를 균등 스텝(각 구간 시작점의 토큰 보존율 100→50→25%)으로 나누고, A.X-Encoder `max_length` 스윕 지점(512/1k/2k)과 정렬한다. **binning 축은 KoBERT 토큰 길이로 고정** — 검증 대상인 512 truncation 경계가 baseline 토큰으로 정의되므로, 두 모델을 같은 문서 분할 위에서 평가한다.

| bin | 토큰 길이     | train          | val         | test        | truncation 정도  | macro-F1            |
| --- | --------- | -------------- | ----------- | ----------- | -------------- | ------------------- |
| B0  | ≤512      | 57,786 (28.6%) | 3,193 (28.6%) | 3,197 (28.4%) | 무손실 (control)   | ✅                   |
| B1  | 512–1,024  | 93,341 (46.2%) | 5,174 (46.4%) | 5,183 (46.0%) | 경미(50–100% 보존) | ✅                   |
| B2  | 1,024–2,048 | 40,966 (20.3%) | 2,279 (20.4%) | 2,342 (20.8%) | 중간(25–50%)     | ✅                   |
| B3  | >2,048     | 9,802 (4.9%)   | 516 (4.6%)  | 549 (4.9%)  | 심함(<25%)       | ⚠️ 문서 적음(test 549) → micro 위주 |

- 실측(`edges=[512,1024,2048]`, `np.digitize(..., right=True)` → 512는 B0). 세 split 구성비 동일.
- **HF 반영**: `ingyoun/patent-clean-text`에 문서별 `kobert_len`(canonical 길이축, SSOT)과 파생 `length_bin`(`<=512`/`512-1024`/`1024-2048`/`>2048`) 컬럼을 추가해 push. 평가는 `document_id`로 조인해 이 축으로 슬라이스하고, 다른 경계가 필요하면 `kobert_len`에서 재-bin한다.
- 벤더 예시 구간(`≤512/512–2k/2k–8k/>8k`)은 이 분포에 부적합: `512–2k`가 ~66%를 한 칸에 뭉쳐 gradient를 가리고, `>8k`는 <0.3%(test max 9,326)라 macro-F1이 통계적으로 무의미.
- **검증 로직**: `Δ(A.X − KoBERT)`가 B0에서 ≈0, B1→B3로 단조 증가하면 장문 가설 지지. 전 구간 균일 개선이면 장문 효과가 아니라 모델 자체 성능차(반증 신호). 길이 슬라이스는 A.X 내부 `max_length` ablation과 세트로 해석.
